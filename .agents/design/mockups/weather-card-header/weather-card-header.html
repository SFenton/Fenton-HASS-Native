The temperature gets cut off when the condition is long

On a 353 pt card at the default text size, "Partly Cloudy" is enough to squeeze the big number down to "4…". This page shows why it happens and four ways to fix it, drawn at real size.

What is going wrong

The numeral is marked layoutPriority(1) with a comment that the condition wraps first. But that modifier sits inside the Button that wraps the glyph and numeral, so the outer HStack in WeatherCardContent.header never sees it. To the outer stack the button and the condition column both have default priority, and the one-line numeral is the one that gives way.

I rebuilt that header as a stand-alone SwiftUI layout at iOS point sizes (it mirrors the code, it is not the app) and it reproduces the report exactly. Moving the priority onto the button fixes the default size, but it is not enough on its own:

What the guidance asks for

The Apple HIG and the repo's own invariants agree on the shape of the fix. The numeral is the card's one hero, so it is the thing that must never lose width, and the secondary text is what adapts.

Recommendation

Your rule is that the temperature never truncates and the condition never wraps below accessibility sizes. Only D meets it. A wraps the label. B stacks and wraps at xxxLarge. C looks right at default size but wraps "Weather Unavailable" at xxxLarge (checked, not drawn above). D keeps one line at every non-accessibility size and the numeral is never in contention, because the numeral and the label sit in separate columns and only the label scrolls.

The cost is that D adds motion the app does not have yet, and the header's left column gets taller (see the height row). So I would build D, with the conditions below. If the motion is a deal-breaker, A is the smallest fix that still ends the clipping.

What D asks of the app

  • Only the label moves, only when it overflows. Measured against the column, never keyed to label strings or sizes, so translations, three-digit temperatures and unmapped provider conditions all take the same path. Constant 30 pt/s, 1.5 s hold at each end, soft fade on both edges while it moves.
  • Finite, not endless. Plays when the card first appears and when the condition text changes, three passes, then rests at the start. The app's motion rules say to animate change, not presence, and WCAG 2.2.2 expects a way to pause auto-moving content that runs past five seconds. The mockup above loops forever so you can watch it.
  • Pauses while the page scrolls, when the card is off screen and when the scene is inactive.
  • Reduce Motion: no ticker. The label wraps to two lines (last card in the carousel row), which is the only way to show all of it without motion. This is the one place the "never multi-line" rule gives way besides accessibility sizes.
  • The range never truncates or scrolls. It stays on one line under the condition. At xxxLarge it needs about 142 pt and the column has about 179 pt, so it fits; if it ever does not (a three-digit temperature at a very large size), the header uses the stacked layout, the same switch as accessibility sizes.
  • The glyph lines up with the label's left edge. The mockup draws the glyph from its ink edge. The real SF Symbols do not: measured at 40 pt, the ink starts 2 to 5 pt in from the symbol's frame (cloud.sun.fill 2.25 pt, cloud.rain.fill 3 pt, wind 5 pt), so a plain Image sits visibly right of the text. The fix is a small table of leading insets per condition symbol in WeatherSymbols (as a fraction of point size), applied as negative leading padding on WeatherGlyph, plus a hosted test that renders each symbol, measures its ink edge and fails if the table is off by more than half a point, in the same style as the existing symbol-name test.
  • Accessibility sizes: the glyph, numeral and chevron share the top row and the label sits under them at full width and wraps (AX2 card).
  • VoiceOver is unaffected. The card button already speaks the condition and temperature, and the ticker text is hidden from accessibility.
  • Motion rules: a constant-speed loop is outside the 0.4 s limit and the "no animating while scrolling" rule in .agents/design/motion.md, so that file needs an explicit ticker exception and a token. Per your standing rule it ships with signposts, XCTest performance metrics (hitches with the ticker running, scroll cost on Home with it) and a devcap runner.
  • Tests: unit tests for the overflow decision and pass counting; UX and accessibility tests on iPhone, iPhone Duo and iPad for: numeral never truncated at Large, xxxLarge and AX5; label on one line below AX; ticker starts only on overflow; Reduce Motion wraps; 44 pt target.
If you choose A instead: implementation sketch

Replace the outer HStack / AnyLayout choice in header(current:night:) with one small Layout that places the hero at its ideal width, asks the trailing block for its narrowest size (propose zero width), and keeps it beside the hero only if that still fits; otherwise it goes below, leading aligned. The range text gets lineLimit(1) and fixedSize.

// Sketch only, not compiled.
struct WeatherHeaderLayout: Layout {
    func placement(in width: CGFloat, _ s: Subviews) -> (beside: Bool, hero: CGSize, trailing: CGSize) {
        let hero = s[0].sizeThatFits(.unspecified)
        let narrowest = s[1].sizeThatFits(.init(width: 0, height: nil))
        let beside = hero.width + HassTokens.Spacing.m + narrowest.width <= width
        let room = beside ? width - hero.width - HassTokens.Spacing.m : width
        return (beside, hero, s[1].sizeThatFits(.init(width: room, height: nil)))
    }
}

Three decisions for D. (1) Three passes then rest, or loop for as long as the card is on screen? (2) Reduce Motion wraps to two lines, or stays on one line with a trailing fade and the full text in the sheet? (3) Accept the header being a little taller because the range now stacks under the condition? I have not changed any app code yet.
