# Camera streams

> **What:** how live camera video is shared, started, stopped and brought back. **Read when:** touching `CameraStreamPool`, `CameraLiveModel`, a camera tile or the viewer, or anything that asks Home Assistant for a stream.

- **One stream per camera.** `CameraStreamPool` owns one `CameraLiveModel` per camera; every tile and the viewer show it. Once shown it is retained for the session (`CameraStreamRetention`); a stream that fails every mode drops its retention. Views call `pool.appear` / `pool.disappear` and never start a stream themselves.
- **Modes.** WebRTC through go2rtc (`auth/sign_path` then `/api/webrtc/ws`), then HLS (`camera/stream`), then the snapshot. Each mode has a first-frame timeout.
- **Never blank, never re-fade.** The snapshot (`CameraSnapshotView`) is drawn over the player whenever the phase is not live, and the player is the only thing that changes. So whatever stops a stream must also move the phase off live (`CameraLiveModel.suspend()` on background); a stopped model that still says live is a black frame that reads "Live".
- **Background and return.** Every stream suspends when the app enters the background; on `willEnterForeground` the pool first makes the websocket answer (`HassConnection.ensureLive`), then starts the wanted streams that are not running. Views are not rebuilt and nothing re-fades: the tiles keep their snapshot until the first frame.
- **Commands for a stream must be bounded.** HAKit drops a command caught by a socket reset without ever calling its completion (`HARequestControllerImpl.resetActive` removes non-retry requests), so `await sendCommand` can hang forever. `signPath` and `cameraStreamPath` carry `HassConnection.streamCommandTimeout` (10 s), and a model waits for a connected socket before its first command. Any new "ask Home Assistant, then show it" step needs a timeout the same way.
- **A failed stream retries by itself.** A stream that fails every mode (`onExhausted`) drops its retention, but while a view still shows it and the app is in the foreground the pool tries it again after 2, 4, 8, 16 and 32 s (`CameraStreamPool.defaultRetryDelays`; web `stream-manager.js` reconnects with 2 s doubling, five attempts, and `RtcPilotCamera.tsx` retries). Before, a stream that failed once (WebRTC and HLS both slow on the network right after the app returned) stayed on the snapshot, so the tile never read Live again, until the socket happened to reconnect or the owner opened the viewer's Retry. Attempts reset when the stream goes live, a view appears, the app returns or the socket becomes ready; retries are cancelled in the background. Retries never start behind the connection check.
- **A live stream whose frames stop is restarted (frame-stall watchdog).** Web parity: `public/rtc/stream-manager.js` `FRAME_STALL_MS = 8000` (line 38) and `FRAME_CHECK_MS = 1000` (line 35), `_checkFrames` (lines 434-480: decoded frames from `getStats`, `videoStalled` at 476, then `_handleDisconnect`). `CameraLiveModel` runs one watchdog task per live stream (`Camera.watchdogs` in the census, started on the first frame, cancelled by `stop()`, `suspend()` and every mode change, so none runs in the background); once a second it reads a frame count and feeds `HassCore.FrameStallDetector` (pure; 8 s without the count advancing). WebRTC counts decoded frames in `WebRTCFrameMonitor` (already called on the decoder thread, one locked increment, nothing on the main thread per frame); HLS uses the player's play position (`currentTime` x 4), which advances while frames do. On a stall the model tears the stream down, puts the phase back to connecting (the snapshot cross-fades back over the player, the tile's live dot goes, the viewer's pill reads "Last live 6:51 PM"; no blank, no re-fade of the page) and calls `onStalled`, and the pool restarts it through its retry backoff (`scheduleRetry`, shared with failed streams). Direction G's "Snapshot from 6:51 PM" pill has no known snapshot time to show, so the pill gives when the stream stopped showing frames. Debug fault injection for journeys: `FENTON_CAMERA_FREEZE_ONCE=<go2rtc stream id>` freezes that camera's reported count the first time it is read while live (the stream itself keeps flowing), once per launch.
- **Every surface uses the pool.** Home's tiles, Security's tiles and the viewer all go through `CameraGrid` / `CameraLiveView` / `CameraStreamPool.shared`, keyed by `HomeConfig.Camera.id` (the entity id). There is no second pool, key or config; do not add one. Measured 2026-10-16 on the iPhone simulator: Home → Security → Home opened exactly one stream per camera (trace: one `open webRTC` each) and Security's tiles read Live and drew frames on first sight (`testSecurityTilesShowTheStreamsHomeAlreadyHas`). `CameraGrid(idPrefix:)` gives Security's tiles `security.camera.<stream>` so journeys can tell the pages apart.
- **Cards are nearly square.** `CameraTile.aspectRatio` is 1 : 0.78 as the web's tile (`CameraTile.module.css`), fill-cropped and centred; a live dot sits in the name label while the stream shows frames. The viewer keeps each camera's own `aspectRatio` and fits.
- **Signalling sockets are released with their stream.** Each WebRTC peer owns a `SignallingSocket` (its own ephemeral `URLSession`, invalidated on `cancel()` and on deinit). On `URLSession.shared` a cancelled socket task stayed allocated (about 170 KB, four per resume, found by the resume-stutter lane 2026-10-16). `Camera.signallingSockets` in the `ResourceCensus` counts sockets whose session has not ended; `SignallingSocketTests` cycle four sockets six times and the count returns to its baseline, and `ResumeCyclesJourneyTests` bounds it at four (one per camera).
- **Restart rules** (the pool's `startStalled`): when the socket becomes ready again (`HassConnection.didBecomeReadyNotification`) or the app returns, start each wanted stream that is not running or has failed. Streams that are live or still connecting are left alone, so a healthy stream is never rebuilt and launch does not start twice. Nothing starts behind a backgrounded app or ahead of the connection check.
- **Teardown must release what the system keeps.** `tearDownPlayers` empties an HLS `AVPlayer` (`replaceCurrentItem(with: nil)`, video output removed) before dropping it: dropping it alone left four notification observers' worth of AVFoundation state, 16 timebases and 4 listener keys behind per restart (heap census, [resume-lifecycle](resume-lifecycle.md)). Each model reports `Camera.players`, `Camera.attempts` and `Camera.observations` and the pool `CameraPool.*` to the `ResourceCensus`; `CameraStreamPoolTests` cycles background and return and requires the set to match the first launch. Open: a `WebRTCCameraPeer`'s signalling `URLSessionWebSocketTask` object stays allocated after `stop()` (four per resume, memory only).
- **Tracing.** `CameraTrace` writes the lifecycle (start, suspend, mode failures, resume) to the unified log (`com.sfenton.home`, category `Cameras`) and, in Debug, to the app group's `push-trace.log` ([push](../platforms/apple/push.md), "Debugging on a phone") with the connection's status changes. Read it first when a camera "does not come back".
- **Tests.** Pool lifecycle, sharing across surfaces and retries with a fake opener: `HassUITests/CameraStreamPoolTests.swift`. Socket checks: `HassCoreTests/HassConnectionLivenessTests.swift`. Device journeys: `CameraJourneyTests` (`testHomeTilesResumeAfterALongBackground`, `testViewerResumesAfterALongBackground`, `testReturningFromBackgroundResumes`, `testSecurityTilesShowTheStreamsHomeAlreadyHas`, `testCardsAreNearSquareAndTheViewerKeepsItsAspect`, `testAStalledStreamFallsBackToItsSnapshotAndComesBack`); stall rule: `HassCoreTests/FrameStallDetectorTests`, watchdog and restart with a fake frame source: `CameraStreamPoolTests` (Frame stalls); the long ones background the app for 60 s, past `ConnectionLifecycle.backgroundGrace`, which is what killed the old restart.
