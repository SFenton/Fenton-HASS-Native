# Apple accessibility audits

> **What:** audit rules and evidence (from FestivalNativeApps). **Read when:** writing the accessibility test a UI change ships with.

- Run XCTest `performAccessibilityAudit()` (all types; `FentonHomeApp.audit` runs contrast as its own pass, because alongside the Dynamic Type or text-clipping checks contrast issues can lose their element and then cannot be measured). No blanket waivers and never a whole audit type. Accept a specific issue only with same-run evidence that disproves it (e.g. rendered contrast measured ≥ 4.5:1 from the screenshot), recorded here with the reason.
- Named visible text over camera images or materials gets a rendered-pixel contrast assertion (≥ 4.5:1 text, ≥ 3:1 meaningful edges); token math is not rendered evidence.
- Large text: assert real glyph growth (> 1.35× at AX5) and that actions stay reachable in every supported orientation.
- Never write `.accessibilityHidden(someBool)`: `false` on an ancestor un-hides descendants. Hide with a conditional modifier that only ever applies `true`.
- XCUITest cannot prove a SwiftUI view is hidden; assert hiding in a hosted test.
- iPad landscape: `XCUIScreen` returns the portrait panel buffer with orientation `.left`. `RenderedContrast` turns frames into it; never sample a landscape capture with screen coordinates (it measured unrelated pixels and both passed and failed elements, 2026-10-10). Exported attachments of that capture also look cropped; use the host capture (`FENTON_CAPTURE_DIR`) for review screenshots.
- Raise superscript text (units) with an `alignmentGuide`, not `baselineOffset`: the offset stretches the element's frame well past its glyph and the contrast audit judges the empty part (thermostat dial `°F`, iPad).
- XCUITest can only `adjust` slider elements, so a custom adjustable control (`accessibilityAdjustableAction`) is tested in the app-hosted `apple/Apps/iOSTests` bundle: host the view in a window, find the element by identifier and call `accessibilityIncrement()` / `accessibilityDecrement()`. SwiftUI publishes its tree there only with accessibility automation on (`_AXSSetAutomationEnabled`); without it a fresh simulator exposes nothing. Example: `ThermostatDialAccessibilityTests`.
- A single passing run of a flaky audit is not certification; a source-identical rerun must pass too.
- iPhone Duo: `XCUIDevice` cannot fold or rotate the Duo. Set the pose in Device Hub before the run; the journey audits the pose it finds.

## System accessibility settings

- **Reduce Motion** (HIG Accessibility, Motion): every implicit animation that moves, scales or resizes goes through `.motionSafeAnimation(_:reduced:value:)` (`HassDesign/MotionSafeAnimation.swift`), never a bare `.animation(_:value:)`. With Reduce Motion on it applies `reduced` (nothing by default; pass a short `.easeInOut` only for an opacity cross-fade). Transitions that slide switch to `.opacity`; `withAnimation` blocks guard on the environment value (`reduceMotion ? nil : …`). A pressed state that scales dims instead. The arc spinner is the one exception: it keeps turning at half speed so it never reads as frozen (owner, 2026-10-14). `ContentGate`'s `withAnimation` blocks are opacity-only under Reduce Motion (its 4 pt rise is dropped), so they stay.
- **Journey launch options.** `FentonHomeApp.SystemSetting` (`reduceMotion`, `reduceTransparency`, `increaseContrast`, `boldText`) with `SystemSetting.environment(_:)` or `FentonHomeApp.allSystemSettings`, passed as the launch environment (`launchSignedIn(environment:)`, `launchGallery(_:environment:)`). UIKit's `-UIAccessibilityReduceMotionEnabled YES` family does **not** reach SwiftUI's environment or the system materials (probed on the iOS 27.1 simulator, 2026-10-15: all four stayed off), so the debug app sets the simulator's own settings from `FENTON_SYSTEM_SETTINGS` through `libAccessibility` (`Apps/iOS/DebugSystemSettings.swift`, Debug builds only; the same private-symbol route as `_AXSSetAutomationEnabled`). All four take effect.
- **The settings belong to the simulator, not the app.** Every journey launch states them (`makeApp()` sends `none`), so the next launch always starts clean, and journeys that turn settings on restore them in `tearDown`. A crashed run can leave them on; the next journey launch clears them. Other lanes' runs on the same pool simulator see them only until their next launch.
- `SystemSettingsJourneyTests` proves the options took effect against the `system-accessibility` gallery page (`FENTON_GALLERY=system-accessibility`), which prints what the app's environment reports. Run it first when a settings-dependent journey fails.
- Reduce Transparency and Increase Contrast also turn `HeaderEdgeFade` into a hard edge and make `Module` opaque; Bold Text widens text, so a clip that appears only there is an AX finding like any other.

## Full-app sweep (`AccessibilitySweepJourneyTests`)

Signed in against the house, read-only (every step opens a page or sheet; nothing is toggled). One test per page so `-only-testing` runs a page alone: the four tab roots (Home, Security, Climate, Chores), Quick Links, Account, the Master Bedroom room page, the Lights chip sheet, Climate Advanced Controls, the Security System sheet, the first Media device's remote, the Humidifier room device sheet, Stephen's Bed sheet, Food and Vacuums. Each runs `FentonHomeApp.audit` (contrast plus the AX5 relaunch). The four tab roots run again under all four system settings (`…UnderSystemSettings`), and check VoiceOver reading order.

```bash
tools/ios_uitest.sh --env <temp.env> --only iphone -only-testing:FentonHomeUITests/AccessibilitySweepJourneyTests   # also --only duo, --only ipad
TEST_RUNNER_FENTON_UITEST_ORIENTATION=landscape tools/ios_uitest.sh … --only ipad …                                   # iPad landscape
```

- **Reading order** (`assertReadingOrder`): the stops are read from one `app.snapshot()` in document order (what VoiceOver swipes through): labelled static texts and one stop per control, tab bar left out. The page title must come before any content (navigation bar buttons such as Profile may come first), and the content after it must not jump back up the page by more than 40 pt, nor run right to left along a row. A stop inside the previous stop's frame is part of the same component. The order is attached to the result (`reading-order-<title>`). A strict row-major rule failed on correct pages (an hour's label then its temperature, a card's own texts), which is why only a clear jump back up counts.
- A label over 128 characters crashes a string-subscript query (`app.navigationBars.buttons[label]`): the Climate Advanced Controls rows are that long. The audit helpers match labels through `XCUIElementQuery.matching(label:)` (a predicate).
- An element-less contrast issue is accepted only when every text-sized labelled static text and button fully on screen (not the tab bar or the Duo rail, not photo-sized frames, whose median surface says nothing about a caption) measures at least 4.5:1 rendered in a capture from the same run (`lowestVisibleText`); the note is logged, and a failure lists the texts that measured low. Added after the live Vacuums page returned two element-less contrast issues at default settings on iPhone while every text measured 5.5:1 or better and the page passed under Reduce Transparency or Increase Contrast alone and in the gallery (2026-10-15). Text more than half inside the floating action bar's strip is accepted at any reading (the bar's scroll edge fades it).
- `ScreenshotPrivacy` redaction is off in the galleries: their data is synthetic and journeys assert the states they show; with it on, Security journeys saw "Hidden" for the alarm state.

- The audit handler only collects issues; every rule above runs after `performAccessibilityAudit` returns. Element queries inside the handler count against the audit's own deadline: on the scrolled iPhone vacuum Auto-Clean tab they made it fail "to complete in time" every run (2026-10-12), while each audit type alone took under 3 s.
- A contrast reading below 4.5:1 is measured again against a fresh capture before it counts: the audit scrolls long sheets to inspect elements, so the frame it reports can belong to a later scroll position than the capture taken when the audit started (iPad vacuum sheet, 2026-10-12: "Status" and "Docked" at 19:1 on screen measured 1.2:1). The higher reading wins; text that really renders low still fails.
- `RenderedContrast` draws the screenshot through `UIImage` so the capture follows the interface orientation; the raw `CGImage` stays portrait in landscape and sampled the wrong pixels (every iPad landscape text measured ~1:1, 2026-10-11). The upright capture's orientation is then `.up`: keeping the raw `.left` turned frames twice and measured every landscape text at 1.0:1 again (2026-10-11).

- **Identifiers on containers replace their children's.** `.accessibilityIdentifier` on a `Section`, or on a view after a `safeAreaInset`, is applied to every element inside and overwrites their own identifiers (seen 2026-10-11: the inventory editor's steppers and switches all read `inventory.editor.batch`; Add Item's footer buttons read `scan.barcode`). Put the identifier on a leaf (a header) or on the view before the inset, or add `.accessibilityElement(children: .contain)` first.
- SwiftUI drops `.accessibilityIdentifier` on an alert's `TextField`; journeys find it as `app.alerts.textFields.firstMatch`.
- The app accent (66,169,254) reads about 2.5:1 as button text on white. Inventory sheets tint with `FloatingActionBar.tint` (5.8:1).
