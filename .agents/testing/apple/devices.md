# Device matrix

> **What:** the simulators every journey runs on and how to run them. **Read when:** running UI or accessibility tests.

| Family | Simulator pool base (pin with env) | Orientation | Notes |
|---|---|---|---|
| iPhone | `iPhone 17 Pro` (`FENTON_SIM_IPHONE`) | Portrait only; `LayoutJourneyTests` proves it stays portrait | |
| iPhone Duo | `iPhone Duo` (`FENTON_SIM_DUO`) | Any | Needs Xcode 27.1+; set folded/unfolded and rotation in Device Hub before each run |
| iPad | `iPad Pro 11-inch (M5)` (`FENTON_SIM_IPAD`) | Any | Journeys rotate to landscape themselves |

```bash
tools/ios_uitest.sh --env /path/to/temp.env            # all three, one simulator at a time, waiting for capacity
tools/ios_uitest.sh --env /path/to/temp.env --only duo  # one family
```

- `--env` reads credentials locally and passes them as `TEST_RUNNER_FENTON_HASS_*`; signed-in journeys skip without them. Never print, log or commit them.
- The script compiles once under a `build` slot, then runs each family under its device gate and a `simulator` slot ([capacity](../../platforms/apple/capacity.md)); it waits when the Mac is full. Anything else that boots or drives a simulator (pose setup, host captures) goes inside `python3 tools/devcap.py run --sim <UDID> -- …`. Never touch other projects' simulators.
- Result bundles land in `apple/.build/uitest-<family>.xcresult` (git-ignored).
- The simulator stays booted (warm) after `tools/ios_uitest.sh`, so consecutive runs on the same device skip the boot and a Duo pose set in Device Hub survives into the next run (folded → unfolded portrait → unfolded landscape). It counts against the simulator slots and is shut down after 60 s idle when another lane is waiting, 5 min idle otherwise, or at once if the run hangs past its hold. A full-suite run (no `-only-testing`/`-skip-testing` filter) shuts the simulator down when it finishes. When you're done with a device after filtered runs, run the last one with `FENTON_SHUTDOWN_SIM=1`, or `python3 tools/devcap.py run --sim <UDID> --shutdown -- true` ([capacity](../../platforms/apple/capacity.md)). `FENTON_KEEP_SIM` is no longer needed.
- Use the product Duo `FENTON_SIM_DUO="iPhone Duo (HASS)"`; the bare `iPhone Duo` device is shared. Without an override each family runs on a free member of its pool (`<name>`, `<name> (pool 2)`, …), so lanes on the same device type run in parallel ([capacity](../../platforms/apple/capacity.md)).
- Unfolding `iPhone Duo (HASS)` (worked 2026-10-16): FestivalNativeApps' `ios_sim.py pose --set unfolded` only knows its own `iPhone Duo (FST)` (`HUB_DEVICE_NAMES`), so wrap it without editing that repo: a script that imports `ios_sim`, sets `ios_sim.HUB_DEVICE_NAMES[<HASS Duo UDID>] = "iPhone Duo (HASS)"` and calls `ios_sim.main(["pose", "--device", <UDID>, "--set", "unfolded"])`, run inside `python3 tools/devcap.py run --sim <UDID> --hold 600 -- python3 <script>`. It needs the Accessibility permission, takes about a minute, and the Duo comes up unfolded **landscape**. The next `tools/ios_uitest.sh --only duo` keeps the pose while the simulator stays booted. To look at the inner display with the app signed in, launch it with `SIMCTL_CHILD_FENTON_UITEST_RESET=1` and `SIMCTL_CHILD_FENTON_HASS_TOKEN` (read from `temp.env`, never printed) and capture `simctl io <udid> screenshot --display=primary-1`.
- Do not edit `apple/` while an `xcodebuild test-without-building` run is going: the package reload can make the run hang or restart. A hung `xcodebuild` also keeps its devcap hold; kill it to release the slot.
- Device Hub can be driven by FestivalNativeApps' `tools/device_hub_ax.swift` helper (via `ios_sim.py`'s `set_duo_pose`, pointed at the HASS Duo) with the Accessibility permission; poses verify by which panel is lit (`simctl io --display=primary` outer, `primary-1` inner).
- Screenshots: set `TEST_RUNNER_FENTON_REDACT_PRIVATE=1` and `TEST_RUNNER_FENTON_CAPTURE_DIR=<dir>` and answer each `<name>.ready` with `xcrun simctl io <udid> screenshot [--display=…] <dir>/<name>.png` then `<name>.done`; the lit Duo panel is only reachable from the host.
- Screenshots are never committed (owner, 2026-10-13). Capture to a scratch directory and attach them to the thread reply; `screenshots/` is git-ignored, so never `git add -f` one. The old `docs/screenshots` tree was removed for this reason.
- Journeys subclass `JourneyTestCase` (`Apps/iOSUITests/JourneyTestCase.swift`): it owns `continueAfterFailure`, the landscape pass (`TEST_RUNNER_FENTON_UITEST_ORIENTATION=landscape` rotates iPad, or the families a journey lists in `rotatingFamilies`), the reset to portrait, `layout` for screenshot names, and the `element`, `lastCall`, `expectLastCall` and `assertTarget` helpers. Do not redeclare them; move a journey onto the base when you next touch it (audit 2026-10-13).
- A signed-in journey reaches a section with `openSection(_:title:in:)`, never by looking only in `app.tabBars`: iPad and the unfolded Duo hide the tab bar and navigate through the flyout (`nav.open`, then `nav.<section>`), and the folded Duo's vertical bar is a toolbar to XCUITest. A tab-bar-only lookup passes on iPhone and fails everywhere else (Security journey, 2026-10-14).
- On the folded Duo the tab bar is a vertical bar that XCUITest reports as a toolbar, and bar items such as Back can move into it. Find tabs through both (`tab(_:in:)`) and go back through `BackButton` or the leading-edge swipe (`goBack(in:)`), never `navigationBars.buttons.element(boundBy: 0)`.
- On the unfolded Duo (Xcode 27.1, iOS 27.1 simulator) a test that throws `XCTSkip` hangs the runner in tear-down for about 3 minutes. xcodebuild then restarts it and reboots the simulator, which comes back **folded**, so the rest of the run silently tests the wrong pose. Run each unfolded pose with `-only-testing` for the journeys that apply to it (no skips), and check the pose after the run. Observed 2026-10-11 in five runs; runs without a skip finished in the pose they started in.
- Under load from several lanes' simulators, the host's simulator framebuffer can crash (`backboardd` in `SimFramebuffer __SFBConnectionConnect`, "Critical process backboardd crashed"), which also reboots the device. It is not an app failure: rerun the affected journeys.
- iPhone Duo poses (seen 2026-10-11): the simulator boots folded, and `tools/ios_uitest.sh` shuts it down after a run, so set the pose again before each run. Device Hub's unfold from a fresh boot gives unfolded **landscape**; rotate left from there for unfolded portrait. `ios_sim.set_duo_pose` often reports "unknown" under load, so confirm the pose by which panel is lit (`simctl io <udid> screenshot --display=primary` is the outer panel, `primary-1` the inner) and its aspect, before and after the run.
- Host captures (`FENTON_CAPTURE_DIR`) use `simctl io screenshot --display=primary-1` for the unfolded Duo; XCUIScreen captures the dark outer panel there.
- iPad host captures (`simctl io screenshot`) can return a rotated framebuffer: a "portrait" capture came back landscape-shaped. For iPad, use the `XCTAttachment` from the result bundle instead (`xcrun xcresulttool export attachments`), named `<name>-<orientation>` (seen 2026-10-12).
- After a mid-run crash restart (`Restarting after unexpected exit`), the Duo comes back **folded**, and its host captures go black on `primary-1`. Treat results after the restart as invalid for an unfolded pose; split unfolded runs into small `-only-testing` groups. Device Hub verification often reads "unknown"; confirm the pose by panel brightness (inner lit and outer dark means unfolded).
- Sheets open at their content height (owner, 2026-10-16; [modal-sheet](../../patterns/modal-sheet.md)), so a journey must not assume a full-height sheet: measure the sheet's scroll view (`scroll.frame.height`) rather than the window, and never `swipeDown()` a sheet's content "to get back to the top" unless the header is off screen (`for _ in 0..<6 where !header.isHittable`): at the top of a content-height sheet that gesture drags the sheet closed (the Sort sheet journey did). `ModalSizingJourneyTests` (gallery `modal-sizing`) holds the sizing, tab bar icon, confirm-state and header assertions on all three families.
